# Endpoint identity

AuthSurface freezes multi-method representation as method-specific records. A route endpoint with methods `POST, GET` becomes two records: one for the normalized route plus `GET`, and one for the normalized route plus `POST`. Methods are uppercased with invariant culture and sorted ordinally before records are emitted.

The durable v1 identity is a deterministic canonical representation of the runtime `RoutePattern` structure plus HTTP method. It is not a proof of general route-matching semantic equivalence. AuthSurface uppercases route literal content, parameter names, and HTTP methods for identity purposes. The readable route preserves its normalized source casing and includes merged defaults and parameter policies. Display names, controller/action names, source locations, endpoint order, and generated display text are never baseline keys. Literal braces are escaped when a readable route is persisted (`{{` and `}}`); this keeps a literal-brace segment distinct from a parameter segment. The readable route is normalized to an absolute pattern with one leading slash; slash characters inside parameter defaults, constraints, and regex payloads are preserved.

Schema version 1 requires every endpoint record to contain `route`, exactly one `methods` value, `authorization`, `policies`, `roles`, `schemes`, explicit JSON booleans `usesDefaultPolicy` and `usesFallbackPolicy`, `requirements`, and `requirementFingerprint`. Missing, `null`, or wrong-type required fields fail as `baseline-field-type`; an omitted boolean is never treated as `false`. The writer and the default `Read`/`Compare(path)` path share a 1,048,576-byte UTF-8 document bound. `Write` serializes and validates the complete document, including that bound, before creating a destination directory or file, so an oversized or malformed write has no destination side effect. A caller may supply a smaller explicit `Read` bound when intentionally imposing a stricter limit.

When display text cannot reconstruct programmatic provenance, the writer includes a bounded `v1:` identity token. Its payload contains a length-delimited binding for every route part, parameter flag/default, policy provenance/content, and HTTP method. The reader decodes that binding and reconstructs a `RoutePattern` through the same `RoutePatternFactory` construction path used by the writer; content-less generated policies are reconstructed through the supported parameter-policy registry. For a non-encoded catch-all with no policy or a textual/content-bearing policy, where the framework exposes parsing rather than a public factory constructor, the reader parses the writer-rendered route and still requires the complete writer binding to match. It then runs the writer's binding extraction and the same canonical renderer used by the writer, and requires the supplied token to match byte-for-byte, including both base64url layers and the canonical UTF-8 length encodings. It accepts the token only when reconstruction succeeds, the emitted binding bytes are identical, and the display and structural renderings match exactly. Thus writer-enforced parameter-name, flag/default, catch-all, segment/part, and generated-policy-provenance rules are enforced by the framework factory and registry rather than a second reader-only validator. If reconstruction throws or cannot prove writer output, the token is rejected as `baseline-malformed` without rewriting the file. Consequently `:`, `=`, parentheses, regex character classes, escapes, slashes, and marker-like text are opaque policy/default payload; no display scanner strips or reclassifies them. Unused base64url pad bits, forbidden padding, non-minimal lengths, redundant structural entries, and any malformed, stale, unsupported, or ambiguous token are rejected as `baseline-malformed` without rewriting the file. Older v1 records without an identity field remain readable; legacy identity tokens are accepted only when the route parser or exact route text proves the binding, and ambiguous legacy tokens fail closed until the baseline is explicitly regenerated.

The persisted-baseline writer has a deliberate narrower boundary: a non-encoded catch-all combined with any generated/content-less policy from the supported registry is not losslessly reconstructable because the framework parser changes that policy's provenance. `AuthSurfaceBaseline.Create` rejects this shape before creating a directory or file with `unsupported-parameter-policy`, identifying the route and HTTP method and directing the caller to use an encoded catch-all, a textual/content-bearing policy, or an explicit exclusion. This covers scalar, composite, optional, regex, and HTTP-method generated policies. The reader remains strict and rejects forged or non-writer-emittable tokens as `baseline-malformed` without changing input bytes.

The persisted token grammar is `v1:<base64url-no-padding(UTF-8(display-route) + U+001E + b1:<base64url-no-padding(binding)>)>`. A `b1` binding begins with the fixed ASCII magic `ASIB` and version byte `1`, followed by the method, canonical structural route, and ordered route-pattern segments. Strings use the bounded UTF-8 length encoding of the .NET binary writer; counts, booleans, part kinds, catch-all flags, optionality, defaults, and content-versus-generated policy records are encoded explicitly. This inner encoding is an implementation-owned v1 contract: readers reject unknown versions, unknown part kinds, trailing bytes, over-bound strings/counts, non-minimal length encodings, non-canonical base64url bytes, redundant zero-width route parts, any binding that the route factory or generated-policy registry cannot reconstruct, and any re-render or byte-for-byte writer-encoding mismatch.

The canonicalizer deliberately keeps policy provenance at the identity boundary. Every content-bearing policy reference is textual and is represented with a `text:` prefix, including an exact-lowercase value beginning with the reserved `programmatic:` marker. A programmatic policy without textual content is rendered by the supported registry and represented with a `programmatic:` prefix; on read, the marker and content must reconstruct through that registry and re-render identically. Thus `text:programmatic:int` and `programmatic:int` are distinct identities even when their readable route display is the same. AuthSurface therefore does not claim that parsed `int` and `IntRouteConstraint` are equivalent, and it cannot infer the meaning of a textual token when an application remaps it with `RouteOptions.SetParameterPolicy`. Built-in textual tokens are case-insensitive, so `iNt` and `int` have the same bounded textual identity. One-value and equal-range length constraints (`length(3)` equals `length(3,3)`), HTTP-method constraint casing/order/duplicates, and composite-constraint child order are also normalized. Constraint arguments, defaults, catch-all encoding, optionality, regex text/options, and other representation details remain identity-significant unless one of those explicit rules applies.

Regex text is one inline framework argument: commas in a pattern, quantifier/range syntax, and literal `;options=` text remain pattern content. Inline regex content is never rewritten as `RegexOptions.None`. Supported programmatic regex policies use the unambiguous `regex64(<base64url-no-padding(UTF-8 pattern)>;options=521)` representation and the framework's inline defaults (`IgnoreCase | CultureInvariant | Compiled`, numeric value `521`); other option combinations fail closed with `unsupported-parameter-policy`. The URL-safe base64 payload cannot contain the private grammar delimiters, so the same representation round-trips inside nested `optional(...)` and `composite(...)` policies without interpreting user regex text. Invalid alphabet, padding, UTF-8, or option suffix forms fail closed. This keeps inline `regex(foo)` distinct from a programmatic regex and keeps a literal pattern containing `;options=` distinct from the explicit programmatic representation.

The same renderer handles parsed patterns and programmatically constructed `RoutePattern` instances without `RawText`; `RawText` is never used as a lossy shortcut. An encoded-slash catch-all is rendered with one star (`{*path}`); a non-encoded catch-all is rendered with two (`{**path}`). A `programmatic:` route-policy marker is an AuthSurface persistence encoding for generated policy provenance, not application route text; structural identity is retained when a route parser would split that marker except for the unsupported non-encoded catch-all/generated-policy combination described above, and it is never reparsed as a claim of framework token-map equivalence. Route policy parsing is bounded per route to a 16,384-character route, 8,192-character policy expression, depth 32, and 100,000 work operations. Each scan additionally bounds cumulative route-rendering/policy-expansion work and authorization metadata items to 100,000 units each, and charges each requirement-data item before it is materialized, with cumulative expansion capped at 8,192 requirements. A countable callback sequence that exceeds the per-endpoint 100,000-item limit is rejected before enumeration; all other above-limit input fails closed with a structured diagnostic. Scanner-owned cancellation is checked between callback yields. Persisted identities are syntax-, size-, route-, and method-validated, and duplicate route/method records are rejected even when supplied keys differ.

## Programmatic parameter policies

For a programmatically constructed `RoutePattern` whose parameter-policy reference has no textual `Content`, AuthSurface supports the following `IParameterPolicy` runtime types and explicit programmatic identity text. Numeric examples are representative values. Composite child order is normalized; distinct child arguments remain distinct. The persisted-baseline boundary above still applies when one of these generated policies is attached to a non-encoded catch-all.

| Runtime type | Canonical identity example |
| --- | --- |
| `AlphaRouteConstraint` | `programmatic:alpha` |
| `BoolRouteConstraint` | `programmatic:bool` |
| `CompositeRouteConstraint` | `programmatic:composite(int,min(2))` |
| `DateTimeRouteConstraint` | `programmatic:datetime` |
| `DecimalRouteConstraint` | `programmatic:decimal` |
| `DoubleRouteConstraint` | `programmatic:double` |
| `FileNameRouteConstraint` | `programmatic:file` |
| `FloatRouteConstraint` | `programmatic:float` |
| `GuidRouteConstraint` | `programmatic:guid` |
| `HttpMethodRouteConstraint` | `programmatic:httpMethod(GET,POST)` |
| `IntRouteConstraint` | `programmatic:int` |
| `LengthRouteConstraint` | `programmatic:length(3,12)` |
| `LongRouteConstraint` | `programmatic:long` |
| `MaxLengthRouteConstraint` | `programmatic:maxlength(12)` |
| `MaxRouteConstraint` | `programmatic:max(9)` |
| `MinLengthRouteConstraint` | `programmatic:minlength(3)` |
| `MinRouteConstraint` | `programmatic:min(2)` |
| `NonFileNameRouteConstraint` | `programmatic:nonfile` |
| `OptionalRouteConstraint` | `programmatic:optional(int)` |
| `RangeRouteConstraint` | `programmatic:range(2,9)` |
| `RegexRouteConstraint` | `programmatic:regex64(XlxkKyQ;options=521)` |
| `RequiredRouteConstraint` | `programmatic:required` |

Parsed policy text is canonicalized only by the explicit rules above. A content-less reference, unsupported programmatic policy type, or unsupported member inside a composite policy is not omitted: analysis fails closed with `unsupported-parameter-policy`. Exclude the endpoint explicitly or use a parsed constraint or one of the supported programmatic types when a stable identity is required.

Two runtime route endpoints whose bounded canonical identities match are duplicates. Scanning fails with the structured `duplicate-endpoint-identity` analysis error rather than silently selecting one endpoint. Representation differences outside the explicit normalization rules can keep two routing-equivalent endpoints distinct. Endpoint exclusions are explicit and happen before identity validation. Routes that remain different after this rule, such as `/alpha` and `/beta`, retain separate records.

## Requirement identity

Requirement identity is separate from route/method identity. The ordered canonical `Requirements` sequence is its single source of truth: order and framework-preserved duplicates are significant. `RequirementFingerprint` is the SHA-256 fingerprint of only that sequence. Classification, named policies, roles, authentication schemes, and default/fallback provenance are excluded from the fingerprint and produce only their dedicated comparison diagnostics when requirements remain identical.
